# Теоретические вопросы(Вариант 1)

## 1. Объектно-ориентированное программирование (ООП): полное определение

ООП — это методология проектирования, согласно которой программа рассматривается как совокупность объектов, каждый из которых является экземпляром определенного класса, а классы образуют иерархию наследования.

С точки зрения архитектуры, ООП — это способ управления сложностью через децентрализацию управления. Оно базируется на четырех «столпах»:

 - Абстракция: Выделение только тех характеристик объекта, которые важны в контексте решаемой задачи.

 - Инкапсуляция: Сокрытие деталей реализации и защита внутреннего состояния объекта от прямого внешнего вмешательства.

 - Иерархия (Наследование): Структурирование абстракций, позволяющее переиспользовать логику и определять отношения «является частью» или «является разновидностью».

 - Полиморфизм: Возможность использовать объекты с одинаковым интерфейсом без знания об их конкретном типе.

## 2. Объектно-ориентированная декомпозиция

Объектно-ориентированная декомпозиция — это процесс разделения сложной системы на модули, где критерием разделения служит объект, а не алгоритм.

В отличие от алгоритмической декомпозиции (top-down), где система разбивается по шагам выполнения («сначала сделай это, потом то»), объектная декомпозиция выделяет автономные сущности, которые обладают состоянием и поведением. Это позволяет минимизировать связность (coupling) и повысить связность внутри модулей (cohesion).

## 3. Дизайн ПО: определение и примеры

Дизайн (проектирование) ПО — это итерационный процесс создания технического описания системы, которое служит планом для реализации. Это трансформация требований (анализа) в конкретные структуры данных, архитектурные слои и интерфейсы взаимодействия.

Примеры:

 - Архитектурный уровень: Выбор между монолитной архитектурой и микросервисами (решение о разделении зон ответственности).

 - Уровень компонентов: Определение интерфейсов API (например, разработка контракта взаимодействия между Frontend и Backend).

 - Уровень кода: Применение паттернов (например, использование Strategy для смены алгоритмов расчета налогов на лету).

## 4. Магическое число 7 Миллера в контексте IT

Закон Джорджа Миллера гласит, что кратковременная человеческая память способна удерживать в среднем 7 ± 2 объекта. В IT это фундаментальное ограничение когнитивной нагрузки.

Примеры применения (7 штук):

 - Количество аргументов функции: Функция с более чем 7 аргументами становится «хрупкой» и трудной для понимания.

 - Глубина вложенности: Код с вложенностью if/for более 5–7 уровней практически не читаем.

 - Размер команды: Эффективная Scrum-команда обычно составляет 7 ± 2 человека для поддержания качественных связей.

 - Количество методов в классе: Если у класса 50 методов, его сложно осознать как единую абстракцию; логично группировать их.

 - Навигация в UI: Меню с 20 пунктами дезориентирует пользователя; эффективнее группировка по 7 ключевым разделам.

 - Количество слоев в архитектуре: Превышение 7 уровней абстракции (например, в сетевых протоколах) затрудняет отладку.

 - Количество одновременно открытых задач (WIP): Разработчик теряет эффективность, если «в уме» держит более 7 активных задач.

## 5. 5 признаков сложных систем по Гради Бучу

Гради Буч выделяет следующие признаки сложности:

 - Иерархичность: Система состоит из взаимосвязанных подсистем.

 - Относительность примитивов: То, что является элементарным для одного уровня, является сложным для другого.

 - Разделение обязанностей: Компоненты внутри подсистемы связаны сильнее, чем между подсистемами.

 - Наличие паттернов: Использование типовых решений для разных частей системы.

 - Эволюция: Сложная система всегда развивается из работающей простой системы.
